# Data Types

It is important to store data in the appropriate format. Unused space will increase as more records that don't use all of the space are added over time: 1 record, no big deal. 1000000 records... a significantly large portion of the database is not utilized.

This chapter is more of an introduction dump for the various data types. Each major topic here is revisited in more detail in later chapters.

- Space efficiency:

  - Fixed types (e.g. zipcode is char(5)): use when there is very strong certainty that the required field's length won't change. Otherwise the unused bytes/digits will be wasted, like a 10-element array where only the first 2 elements are ever used.
  - Variable length (e.g. last_name is varchar(50)): use when the required space is less certain. Only the necessary space is used, up to the maximum specified

- Author guidelines (for beginners):
  - Use text on all character columns to avoid specifying maximum lengths. BUT beware that TEXT has Postgres-specific behavior, this would not limit input (up to the ~1G built-in limitation). See first line above in these notes.
  - Use bigint generally for most of your integers and you won't need to worry about the number being able to fit. BUT beware that for real-world best practice choose the smallest type appropriate to prevent bloat (see first line above in these notes).
  - Criteria:
    - Use integers when possible (no decimals required)
    - When exact calculations are required, use numeric (or decimal). Floats save space but are inexact
    - For smaller databases (not millions of records), lean towards larger: set the precision to be large enough to handle the digits on both sides of the decimal. Whole numbers: use bigint unless you're certain integer (or smallint) is sufficient.

## TEXT

TEXT: ariable length, stores a string up to about 1 gig

```SQL
CREATE TABLE char_data_type (
  note TEXT
);
```

## Auto-increment integer

2 types:

- IDENTITY (ANSI standard): best practice is to use this method!
  - GENERATED ALWAYS AS IDENTITY: user is not allowed to insert by default
  - GENERATED BY DEFAULT AS ENTITY: allows user to insert a value, otherwise auto-increments it: this is a riskier method because it allows the user to potentially enter duplicate values
- SERIAL (Postgres-specific): predates the ANSI standard (it was ahead of the curve!)

Example: uses the 'protected' ANSI standard IDENTITY for the auto-increment id field:

```SQL
CREATE TABLE table_name (
  id integer GENERATED ALWAYS AS IDENTITY,
);
```

The path is OS-specific (e.g. 'C:\Users\Public\names.txt' or '/tmp/names.txt')

```SQL
-- Import
COPY table_name FROM <local path>
WITH (FORMAT CSV, HEADER, DELIMITER '|'); -- input file format options, '|' is the separator in this example
-- Export
COPY table_name TO <local path>
```

## INSERT Implicit / explicit

Implicit: if the VALUES match the number of columns in the table, they'll be inserted in the order they're defined in the table.

NOTE: This is allowed, but not best practice. It's better to explicitly specify the columns (implicit).

```SQL
CREATE TABLE char_data_types (
    char_column char(10),
    varchar_column varchar(10),
    text_column text
);

INSERT INTO char_data_types
```

## Math Operations

- Sorting: strings (characters representing numbers) sort alphabetically, not numerically like actual numbers
- Integers: can be positive, 0, or negative

### Precision: Precision and Scale

Use numeric() to specify precision (total digits) and scale (digits allocated to the decimal)

```SQL
numeric(<precision>,<scale>)
```

Example: to declare a number with a maximum of 5 digits with 100ths (2-digit) precision:

```SQL
CREATE TABLE table_name (
    numeric_column numeric(5,2)
);
```

## Time

Databases use the server's clock (and timezone, region settings) to calculate time

- timestamp: represents the time and date combined
- interval: represents a measure of time (2 days, 20m, etc.)
- Standard date format: 'YYYY-MM-DD'

```SQL
CREATE TABLE date_time_types (
    timestamp_column timestamp with time zone,
    interval_column interval
);
```

### Casting

CAST(): Casting is allowed, but only if the input values can be interpreted as the target type.

Some examples:

```SQL
-- Timestamp to string:
SELECT timestamp_column, CAST(timestamp_column AS varchar(10))
FROM date_time_types;

-- Number to integer (may work), number to string will work:
SELECT numeric_column,
       CAST(numeric_column AS integer),
       CAST(numeric_column AS text)
FROM number_data_types;

-- Does not work:
SELECT CAST(char_column AS integer) FROM char_data_types;
```

A Postgres-specific shortcut syntax exists for casting using double colon (<from_type>::<to_type>):

```SQL
SELECT timestamp_column::varchar(10)
FROM date_time_types;
```
