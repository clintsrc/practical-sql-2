# Table Design

Organization and consistency help with efficiency

## Naming Convention

Determine your org's naming convention, otherwise be consistent in your own projects:

- camelCase
- PascalCase
- snake_case

### Case sensitivity

Postgres defaults to lowercase. Use qotes if you need specific case, but it's best practice to avoid it:

```SQL
CREATE TABLE "Customers" (
  ...
);

SELECT * FROM "Customers";
```

### Use Plurals for Table Names

Since talbles have multiple rows, it's more natural to use plurals (students, managers, etc.)

### Sensible Descriptor Length

Descriptive names are helpful, but keep the lengh within reason. Each RDBMS has a maximum descriptor length

### Copies of Tables

If you're making a copy / backup of a table, add the date to help you identify it long after you've created it (name_YYYY_MM_DD), and to help with sorting them.

## Constraints

Specifies data allowed in a field (prevents garbage data)

- Data type
- PRIMARY KEY [(ch07)](../Chapter_07/notes.md#primary-key): Column/s that uniquely identify a non-null field
- Foreign Key [(ch07)](../Chapter_07/notes.md#foreign-key): Reference to pre-existing column (usually in another table)
- CHECK: allow rows with specified boolean expression
- UNIQUE: ensure values in column/s are unique in each row
- NOT NULL: prevent NULL values

### Types (Column, Table)

#### Column Constraint: criteria applies only to 1 column. Defined by CREATE TABLE

```SQL
CREATE TABLE natural_key_example (
    -- Column constraint with primary key 'license_id'
    license_id text CONSTRAINT license_key PRIMARY KEY,
--  license_id text license_key PRIMARY KEY, -- omit 'CONSTRAINT' to automatically name as <table_name>_pkey)
    first_name text,
    last_name text
);
```

#### Table Constraint: criteria applies to 1 or more coluns. Defined by CREATE TABLE

``` SQL
CREATE TABLE natural_key_example (
    license_id text,
    first_name text,
    last_name text,
    -- Table constraint is specified after listing all the columns
    CONSTRAINT license_key PRIMARY KEY (license_id)
--  license_key PRIMARY KEY (license_id) -- omit 'CONSTRAINT' to automatically name as
);
```

### Primary Key Types (Natural, Surrogate)

#### Natural

- Existing Columns: existing column/s can be a natural primary key as long as they are unique and non-null.
  - Composite Primary Key: A unique combination of 2 or more fields.

##### Natural: Pros / Cons

- Pro:
  - Data already exists
  - Key data is meaningful (can reduce need to join tables)
- Con:
  - If data changes in a way that breaks the requirement you may be forced to change the table itself

#### Surrogate

- Sequential number, autogenerated [(ch04)](../Chapter_04/notes.md#auto-increment-integer) (e.g. IDENTITY)
- UUID: [Universally Unique Identifier](https://www.postgresql.org/docs/current/datatype-uuid.html). Practically guaranteed to be unique but inefficient compared with other types like biging
  - Surrogate Key: Single column with an artificial value

##### Surrogate: Pros / Cons

- Pro:
  - Not tied to the key structure. If data changes later, it won't effect the key structure.
  - Key values are guaranteed to be unique
- Con:
  - Additional column for key requires more space.
